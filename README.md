# Oportunidades de Financiamiento · PEP Chaco +20

Tablero institucional para las áreas del Gobierno del Chaco que canalizan financiamiento. La consulta pública muestra solo oportunidades aprobadas. La carga y revisión requieren usuarios de Supabase; las operaciones de administrador requieren TOTP (AAL2).

**Estado de la entrega:** código preparado, sin proyecto Supabase conectado. El sitio muestra “Conexión pendiente” hasta completar la configuración. No contiene convocatorias reales ni cuentas creadas. No se publican propuestas automáticamente.

Archivos: [index.html](index.html), [schema.sql](schema.sql), [protocolo-semanal.md](protocolo-semanal.md), [plantilla-semanal.csv](plantilla-semanal.csv). El HTML contiene CSS, JavaScript, logo y mapa; su única dependencia de ejecución es `supabase-js` 2.119.0 por CDN.

## Instalación — 12 pasos

1. **Crear el proyecto.** En [Supabase](https://supabase.com/dashboard), creá un proyecto nuevo, elegí organización y región, y guardá la contraseña de la base en tu gestor de contraseñas. Esa contraseña nunca se pega en el HTML. Elegí un plan disponible según tus necesidades; verificá sus límites en el panel.
2. **Cerrar el registro público.** En Authentication → configuración de proveedores / Sign In & Providers, habilitá email y contraseña y desactivá **Allow new users to sign up**. Desactivá también los inicios anónimos y proveedores que no vayas a usar. La aplicación no ofrece registro, pero este ajuste del servidor es obligatorio.
3. **Crear la base.** Abrí SQL Editor, pegá y ejecutá todo [schema.sql](schema.sql). Es una instalación inicial transaccional para un proyecto nuevo: no vuelvas a ejecutarlo sobre las mismas tablas. No expongas el esquema `private` en la Data API. Conservá `public` expuesto. El SQL instala tablas, RLS, auditoría, funciones de revisión y el perfil inicial `lector`.
4. **Crear el primer usuario.** En Authentication → Users → Add user → Create new user, ingresá tu email y una contraseña robusta; usá la confirmación de email del panel si la interfaz lo solicita. No uses credenciales compartidas. El trigger crea el perfil automáticamente. En SQL Editor ejecutá, reemplazando el email, `update public.perfiles set rol='admin', nombre='Administrador PEP', area='Área responsable' where id=(select id from auth.users where email='TU_EMAIL');`. Verificá que se haya actualizado exactamente una fila. Este es el único ascenso inicial por SQL.
5. **Habilitar TOTP.** En Authentication → Multi-Factor Authentication, habilitá inscripción y verificación TOTP. Conservá el acceso seguro de recuperación al panel Supabase. Cuando ingreses por primera vez al tablero, escaneá el QR con tu aplicación autenticadora e ingresá sus seis dígitos. Sin verificación AAL2 la base deniega la administración, aunque alguien intente llamar directamente a la API. Las recuperaciones de MFA se administran desde Supabase.
6. **Configurar el HTML.** Desde Project Settings / Connect obtené la URL del proyecto y su clave pública `anon` (o publishable). Completá `SUPABASE_URL` y `SUPABASE_ANON_KEY`, al inicio de [index.html](index.html). Son valores públicos; **nunca uses `service_role`, secret keys, contraseñas ni tokens personales**. No hay otras claves que colocar en el navegador.
7. **Publicar el archivo.** Subí el `index.html` configurado a la raíz de `Nico199723/pep-chaco-cooperacion`. En GitHub → Settings → Pages, elegí Deploy from a branch, `main`, `/(root)` y guardá. Usá la URL HTTPS que muestre Pages. GitHub aloja la interfaz; Supabase conserva los datos y aplica los permisos. Los borradores, CSV internos, rechazos y credenciales no se suben al repositorio público.
8. **Configurar la URL de Auth y entrar.** En Supabase → Authentication → URL Configuration, configurá la URL HTTPS publicada como Site URL y permití solo redirecciones necesarias. Abrí el tablero, ingresá con email y contraseña y completá el TOTP del paso 5. El login usa contraseña, sin magic link ni registro público. Para restablecer acceso, usá las herramientas del administrador de Supabase y el procedimiento de recuperación de tu organización.
9. **Crear el resto de usuarios.** Repetí Authentication → Users → Add user para cada persona. En el tablero, Panel de gestión → Usuarios y roles, asigná nombre, rol y área. `lector` ve aprobadas; `editor` crea y edita **sus propias pendientes en el área exacta asignada**; `admin` gestiona todo con TOTP. Usá una denominación de área consistente y específica. Ningún usuario puede cambiar su propio rol sin ser administrador; no se puede degradar al último administrador desde el tablero.
10. **Probar permisos con cuentas separadas.** En una sesión privada sin login verificá que no se vean pendientes, fuentes ni historial. Con editor creá una propuesta de prueba y comprobá que no pueda aprobarla ni editar otra área. Con lector verificá que no tenga gestión. Con admin sin TOTP verificá que la base rechace cambios; completá TOTP y revisá una propuesta de prueba. Probá también llamadas directas a la API y el vencimiento tras 30 minutos sin actividad. Usá un proyecto de prueba para estas verificaciones; no apruebes datos sintéticos en producción.
11. **Cargar y revisar.** Descargá la plantilla semanal, completá los campos e importala como admin. Verás duplicados antes de confirmar. Máximo 25 filas por corrida, ordenadas por puntaje y cierre; el excedente se descarga como “Pendientes de siguiente corrida”. Toda nueva fila queda pendiente. Los duplicados pendientes se omiten. Los rechazos previos se omiten salvo que se declare un cambio sustancial. Los cambios de aprobadas se conservan en una propuesta separada: usá **Fusionar** después de comparar los campos, o rechazala. Aprobar requiere link, fuente primaria verificada y fecha de relevamiento. La aprobación masiva es atómica y admite hasta 25 seleccionadas.
12. **Operar y mantener.** Agregá semillas y candidatas en Fuentes; aprobá o bloqueá con motivo. Exportá rechazos para el próximo relevamiento. Revisá Historial y los cambios/vencimientos. Mantené exportaciones y respaldos de la base según el plan y la política provincial. Después de cambios de esquema o permisos, repetí las pruebas. Actualizá dependencias de manera controlada. Las sesiones del navegador viven en memoria: al recargar o cerrar la página habrá que ingresar otra vez.

## Decisiones de seguridad y datos

- **Acceso público explícito:** se adoptó la sección “Vista pública (sin login)” de la especificación. El login protege la gestión; el contenido aprobado es visible para cualquier visitante. Si todo el tablero debe ser privado, hay que retirar también los permisos `anon` en SQL, no basta con ocultar la pantalla.
- Las políticas RLS se aplican a las tablas. La vista pública usa `security_invoker`; el visitante anónimo no tiene acceso a columnas internas de revisión o autoría. Los lectores autenticados pueden leer filas aprobadas, sin poder escribir.
- El rol nunca se copia de `user_metadata`. Los permisos administrativos requieren rol en `perfiles`, `aal2` en JWT y una sesión activa registrada en un esquema no expuesto. Cambiar el HTML o mostrar botones no altera esos controles.
- La actividad se actualiza con interacción del usuario, no por un temporizador de refresco. Después de 30 minutos sin actividad, RLS bloquea operaciones privadas; el heartbeat no resucita una sesión vencida. El botón Cerrar sesión la revoca además de cerrar Supabase Auth. La vista pública sigue disponible.
- El código no utiliza `localStorage` ni `sessionStorage`. Auth tiene `persistSession:false`; datos, sesión y códigos TOTP no se guardan en el navegador. Un cliente deliberadamente modificado podría enviar actividad artificial, como ocurre con cualquier control de inactividad basado en actividad del cliente; la base igualmente exige JWT válido, rol y AAL2.
- El historial es automático para oportunidades, fuentes y perfiles, con usuario, fecha y valores antes/después. Los clientes no pueden modificarlo ni borrarlo. El propietario de la base en SQL Editor conserva privilegios de mantenimiento: no es un archivo inmutable frente al dueño de la infraestructura.
- `id` es el UUID interno; `codigo` es el ID visible, por ejemplo `INT-2026-001`. Una actualización pendiente puede compartir código con su versión aprobada. Solo puede existir una aprobada por código, link normalizado y nombre+organismo normalizados. La fusión preserva el código y UUID de destino, archiva la propuesta y registra ambas operaciones.
- Los cambios concurrentes se detectan con `version`. Las revisiones masivas y fusiones son transaccionales; una incompatibilidad revierte el lote completo.
- Fechas y montos desconocidos se guardan como `NULL` y se muestran/exportan como “No informado”. Las listas se separan con `;` en CSV. El resumen admite tres líneas y hasta 900 caracteres; el ancho de la pantalla puede envolverlas en más renglones.
- Las vencidas se muestran como Cerradas desde la vista SQL y la interfaz, usando la fecha de Argentina; no se borran ni se requiere un cron para recalcularlas. Se conserva el estado declarado originalmente en la tabla para trazabilidad. La hora de cierre concreta debe confirmarse en las bases.
- La deduplicación identifica links (sin fragmento y barra final), código y nombre+organismo. No sigue redirecciones ni garantiza detectar cambios de URL o redacción: la cola permite revisión y fusión humana. “Cambio sustancial” es una declaración del importador, no una aprobación automática.
- No hay conexión automática de ChatGPT a los datos privados de Supabase. Para el relevamiento, proporcioná las exportaciones actualizadas de rechazos, fuentes bloqueadas y base aprobada. La importación vuelve a contrastar contra la base en el servidor.

## Verificación

Pruebas de PostgreSQL ejecutadas con PGlite y un esquema `auth` simulado: RLS, aislamiento por área, escalamiento de rol, obligatoriedad AAL2, auditoría, aprobación atómica, importación, memoria de rechazos, fusión y sesiones. Pruebas de interfaz con DOM simulado y revisión visual pública en escritorio y 390 px. **Esto no sustituye probar Auth/TOTP contra tu proyecto real**, que todavía no está configurado.

Para repetir los tests de desarrollo: `npm install` y `npm test`. Estas dependencias se usan solo para pruebas; la página publicada sigue siendo un único HTML.
